# Thread Search (Mac + iOS)

Status: approved for implementation
Author: Gary
Date: 2026-07-26

## 1. Problem

Garyx has no way to find a thread by name. Both the Mac app sidebar and the iOS
home list are pure recency feeds with keyset pagination: once a conversation
falls past the loaded window, the only way back is scrolling. Users think in
thread names ("the iOS anchor one", "TASK-2541"), not in recency position.

Requirement: search threads by **thread name**, case-insensitive, substring
("fuzzy") match. One well-placed, native-feeling entry point on Mac and one on
iOS.

## 2. What already exists

`GET /api/thread-summaries` already implements a searchable, keyset-paginated
thread list:

- `garyx-gateway/src/routes/thread_summaries.rs` — params
  `root_workspace_path` / `tasks` / `q` / `cursor` / `limit` (default 30, max
  100, `deny_unknown_fields`); `q` is trimmed, normalized, capped at 100 scalars;
  the cursor is bound to `(scope, tasks, q, incarnation)` so changing the query
  invalidates paging.
- `garyx-gateway/src/garyx_db/summaries.rs` — 12 static SQL branches generated by
  `thread_summary_sql!`, each `INDEXED BY` a partial index for ordering, filtered
  by `WHERE default_list_hidden = 0` and `AND instr(search_text, ?) > 0`, ordered
  `sort_updated_at_us DESC, thread_id DESC`.
- `garyx-gateway/src/thread_meta_projection.rs:112` —
  `normalize_for_search(v) = v.nfkc().default_case_fold()`. Applied on both the
  write side (projection) and the read side (query), so matching is already
  case-insensitive and Unicode-correct (`Straße` ≡ `strasse`, `CAFÉ` ≡
  `Cafe\u{301}`).

Consumers today: iOS automation thread picker only. Desktop never calls it.

So the backend is 90% of the way there. The gap is semantic, plus two missing
client surfaces.

## 3. Decisions

### D1 — Search corpus collapses to the thread name only

Today `search_text` is a four-field blob:
`title \n workspace_dir \n agent_id \n last_message_preview`
(`thread_meta_projection.rs:129-142`).

That is wrong for a feature called "search threads". Typing `gary` matches every
thread whose `agent_id` is `gary`; typing a path fragment matches every thread in
a workspace; typing a common word matches whatever happened to be the last
message. The result set stops being "threads named X" and becomes noise, and the
user cannot tell *why* a row matched because the matching text is not displayed.

**Decision:** `thread_meta`'s search column is derived from the thread label
alone, and is renamed to `search_title` so the column name states its meaning.
There is no second corpus, no mode flag, no "search scope" parameter — one
column, one meaning, one owner.

Consequences, accepted deliberately:

- The iOS automation thread picker's search narrows to titles too. That is a
  product-visible behavior change and it is the correct one: its own placeholder
  says "Search threads", and title matching is what makes its results
  explainable.
- No compatibility shim, no dual column, no "legacy corpus" fallback. Per the
  design rule: change the behavior, state it in the report.

Implementation shape:

- `summary_search_text(...)` becomes `summary_search_title(title)` returning
  `normalize_for_search(title.unwrap_or_default())`.
- `ThreadMetaDraft.search_text` → `search_title`; `meta.rs` insert/upsert/select
  and `thread_runtime.rs:417` follow.
- Schema: add `search_title` column, backfill from existing rows via a new
  versioned one-shot migration recorded in `projection_states`, then drop
  `search_text`. Follow the existing pattern in
  `garyx_db/migrations.rs` (`run_thread_data_startup_migrations`) and the
  column-fallback pattern in `schema.rs:565-610`. The migration must be
  idempotent and must not require a full record re-read if the label is already
  projected in `thread_meta` (backfill can normalize `thread_label` in SQL-driven
  Rust, not by re-parsing thread records).
- `summaries.rs`: the 12 branches change `instr(search_text, ?)` to
  `instr(search_title, ?)`. Keep the macro; do not hand-expand.
- Read side keeps `normalize_for_search` on `q` — unchanged.

### D2 — No new route, no `q` on `/api/recent-threads`

Search reuses `/api/thread-summaries?q=`. `recent_threads` gets no search column,
no migration, and no extra SQL branches.

Rationale: search is a different query mode from the recency feed (different
result ordering rationale, different pagination lifetime, different empty state).
`thread-summaries` already owns keyset search with cursor-query binding and
partial-index ordering. Adding a parallel search path into `recent_threads` would
create a second search implementation with a second corpus — exactly the
duplication D1 removes.

The two projections derive the same title from the same thread record label, so
a row's name in search results matches its name in the list.

### D3 — Search scope is global and includes task threads

Search always issues `tasks=include` with no `root_workspace_path`, regardless of
the list filter the user is currently looking at (Mac: All/Chats/Favorites and
the Threads/Projects tab; iOS: the recent filter menu).

Rationale: "find a thread by name" means all threads. Scoping search to the
active filter would silently hide matches and make an empty result set a lie.
Task threads are real named conversations and are frequently what the user is
looking for (`TASK-2541`); excluding them would be a worse default.

Hidden threads stay excluded — `WHERE default_list_hidden = 0` is already the
list-visibility contract and search inherits it.

### D4 — Server-owned matching; no client-side filtering

Neither client filters titles locally. The loaded recency window is a page, not
the corpus; filtering it locally would return a subset that shrinks as the user
scrolls, which is indistinguishable from a bug. Every keystroke's result set
comes from the gateway.

This also keeps normalization in exactly one place: `normalize_for_search`.

Existing legacy-gateway fallbacks (`GaryxLegacyThreadPickerFallback`,
`probeThreadSummariesCapability`) are **not** extended to this feature and are
**not** touched — they are pre-existing surface outside this scope. New search
does not add any old-gateway compatibility path; an unsupported or failing
gateway surfaces a failure state.

### D5 — Debounce, cancellation, and paging behavior (shared by both clients)

- Empty/whitespace query = not a search. No request is issued; the surface shows
  a prompt state ("Search threads by name"), not an empty-result state.
- Non-empty query is debounced 250 ms (matching the existing iOS picker
  precedent at `GaryxMobileAutomationViews.swift:1040`).
- Every query change invalidates in-flight requests and their cursors. A late
  response from a superseded query must never be rendered — use the platform's
  existing generation/instance-fence pattern, not a timestamp comparison.
- Results page on scroll-to-near-end using the returned cursor, same as the
  recency feeds.
- States are explicit and distinct: `prompt` (no query) / `loading` (first page
  in flight) / `results` / `empty` (query returned nothing) / `failed` (with
  retry).

The state machine above is pure logic and must live in a testable pure module on
each platform (see §6), not inline in view code.

## 4. Mac app

> Revised 2026-07-26 after the first implementation was rejected. The original
> design put a persistent field at the top of the sidebar and swapped the
> sidebar body in place for results, reusing `ThreadRailList`. That is not the
> intended interaction and is superseded entirely by this section. Nothing
> about search should live in the sidebar body, and search results must not
> reuse the sidebar list.

**Shape:** a centered modal search palette over the whole app window —
Spotlight / command-palette form. Opening it dims the app behind it; the panel
owns both the input and its results.

**Entry points:**

- A search affordance in the left rail's primary nav group (same row vocabulary
  as `New Thread` / `Automation` / `Tasks`), which opens the palette. The rail
  keeps no input field and no search mode of its own.
- `⌘K` opens the palette from anywhere in the app. Nothing global claims `⌘K`
  today. `Esc` closes it.

**Palette layout (top to bottom, inside one centered panel):**

- A single large search input at the top of the panel, focused on open, with the
  placeholder naming what is searched (thread names).
- Directly below it, the panel's **own** result list — a result-row component
  built for this panel. Do **not** reuse `ThreadRailList`, `ThreadRailRow`, or
  `threadRailRowsFrom`; the sidebar's row is a rail row with rail affordances
  (inline archive, active-row rail highlight) that do not belong in a search
  result. A result row shows the thread name as the primary line plus enough
  secondary context to disambiguate two similarly named threads (agent/provider
  identity via the shared avatar component, workspace, last activity time).
- The panel is sized for reading a list — a comfortable fixed max width, a
  height that holds roughly eight to ten rows before the list scrolls internally,
  and it never resizes as results arrive (no layout jump between states).

**Behavior:**

- Empty input: prompt state inside the panel. No request.
- Typing: 250 ms debounce, then server search; the list area shows loading,
  results, empty, or failed per D5. The panel's frame does not move between
  those states.
- `↑` / `↓` move the highlighted row, `Enter` opens the highlighted thread,
  `Esc` closes. The highlighted row must scroll itself into view
  (`scrollIntoView({ block: 'nearest' })`), matching the existing slash-command
  list behavior in `ComposerForm.tsx:825-830`.
- Clicking a row opens that thread and closes the palette.
- Scrolling near the end of the result list pages with the returned cursor.
- Closing the palette discards the query; reopening starts clean.
- Empty result copy: `No threads named "{query}"`.

**Constraints:**

- All user-visible strings go through `t(...)` with `zhCN` entries.
- Do not add a focus ring — `*:focus { outline: none }` is a deliberate project
  decision.
- Build the panel from existing UI primitives (`components/ui/dialog`,
  `components/ui/input`) and existing design tokens; do not introduce new colors
  or a bespoke modal implementation.
- The palette is a modal layer over the app. It must not alter sidebar layout,
  sidebar state, or the responsive collapse behavior in any way.
- Revert the sidebar-side changes from the first implementation:
  `SidebarThreadSearch.tsx` and the search mode wired into `AppLeftRail.tsx` are
  removed, and `recent-filter-source-contract.test.mjs` goes back to asserting
  three `threadRailRowsFrom(` call sites.

**Plumbing (already built, keep it):** renderer never speaks HTTP. The
`garyx:list-thread-summaries` IPC → preload bridge → main
`fetchThreadSummaries(settings, input)` chain in
`src/main/garyx-client/threads.ts` is correct and stays as-is, including its
gateway-scope guard. The pure state machine in
`app-shell/thread-search-model.ts` also stays; only its presentation host
changes from a sidebar mode to the palette.


## 5. iOS app

**Placement:** a 44×44 circular glass button (`magnifyingglass`) in
`GaryxHomeHeaderView`, immediately before the existing recent-filter menu button.

**Behavior:**

- Tapping it expands the home top bar in place into a search bar: the search
  field takes the bar's width with a trailing `Cancel`; the menu button, the
  `Garyx` wordmark, and the filter button yield to it. Per the mobile UI rule,
  chrome that expands in place is **one morphing glass surface anchored to the
  collapsed control's rect** (the title-capsule → thread-settings-panel pattern),
  not two views swapped behind a matched-geometry pair. If that mechanism proves
  genuinely unusable here, the alternative must be equally continuous and the
  deviation must be reported — a bare `if/else` view swap is not acceptable.
- The field is focused on expand. `Cancel` collapses back and clears the query.
- The list region shows results with the same `GaryxThreadListRowButton` rows as
  home, including the long-press action menu. Selecting a row opens the thread
  through the shared `GaryxMobileModel.openThread` path. Returning from the
  conversation keeps search mode and the query intact.
- Reuse `GaryxGlassSearchField` (`GaryxMobileStatusComponents.swift:465`).
- Do **not** use `.searchable` — home hides the navigation bar and the project
  has zero `.searchable` precedent.
- Pull-to-refresh stays owned by the recency list; in search mode the refresh
  gesture re-runs the current query.
- Prompt/empty/failed copy mirrors Mac.
- Reduce Transparency and Dynamic Type are layout inputs, per existing helpers.
- Add `accessibilityIdentifier`s on the search button, field, and cancel control
  so the interaction is reachable from XCUITest.

**Plumbing:** `GaryxGatewayClient.listThreadSummaries(query:...)` already exists
and needs no change. The search store must not reuse
`GaryxThreadPickerMembershipOwner` if that would drag picker-selection semantics
or the legacy fallback into home search; a dedicated store that shares the same
provider/fence primitives is preferred.

## 6. Testing

Headless and deterministic. No "open the app and look" as the acceptance
evidence for logic.

**Rust**

- `thread_meta_projection`: title-only derivation, including empty label,
  whitespace label, and NFKC/case-fold equivalence. The existing
  `summary_projection_derives_sort_fallback_and_four_field_search_text` test must
  be rewritten to the new contract, not deleted.
- Migration: backfills every existing row exactly once, is idempotent on re-run,
  records its `projection_states` marker, and leaves no `search_text` column.
- Routes: `q` still trims/normalizes/caps at 100 scalars; cursor stays bound to
  the canonical query; a query matching only a workspace path / agent id / last
  message preview now returns **no** rows, while the same thread is found by its
  title. Extend
  `thread_summaries_instr_search_handles_unicode_literals_nul_and_all_four_fields`
  to the new contract.
- EQP tests (`..._use_scoped_partial_indexes_without_temp_sort`) must still pass.
- Validation: `cargo test -p garyx-gateway --lib` plus the touched route/db test
  modules; `scripts/test/rust_tier1_fast.sh --changed` before handoff.

**Desktop**

- New pure model module (`*-model.ts`) for the search state machine — query
  normalization, debounce decision, request-generation fencing, page merge,
  state derivation (prompt/loading/results/empty/failed) — with a colocated
  `.test.mjs` under `npm run test:unit`.
- Client contract test for `fetchThreadSummaries` response validation.
- `npm run build:ui` (tsc --noEmit) and `npm run test:i18n-literals` clean.
- One packaged-app check (`npm run dist:dir`, then attach via CDP) for the
  sidebar mode switch at 245px and at a normal width.

**iOS**

- `GaryxMobileCore` SwiftPM tests for the search store: debounce decision,
  stale-response rejection after a query change, cursor reset on query change,
  page merge/dedup, and every state transition.
- Gateway client contract test asserting the emitted query items.
- `swift test` from `mobile/garyx-mobile` — report the real executed-test count.
- Simulator walkthrough on the single reference configuration (iPhone 17 Pro Max,
  iOS 26.5, light mode) for the expand/collapse chrome only.

## 7. Out of scope (record, do not fix here)

Anything adjacent found during implementation goes to
`docs/design/thread-search-review-debt.md` with its source location and is filed
separately. Specifically out of scope:

- Searching message content / transcripts.
- Adding search to the Mac secondary conversation rail, the workspace rails, or
  any other list.
- Reworking or removing the existing legacy-gateway picker fallback.
- Highlighting matched substrings inside result rows.
- Search history, recent queries, or suggestions.
